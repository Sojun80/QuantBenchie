# Context sweep: Llama 3.1 8B F16 vs Q2_K

Date: 2026-08-23

## Initial result

Both Llama 3.1 8B variants loaded with a 131,072-token server context when using an 8-bit K/V cache. The F16 model required an asymmetric split across the RTX 5070 and RTX 5060 Ti; a symmetric split ran out of GPU memory. The Q2_K model fit on the larger GPU. These runtime settings must remain fixed for a fair comparison.

The probe placed three known anchors near the beginning of a long prompt, added neutral filler, and asked for all three at the end. Both models returned the correct anchors at every tested level, including the near-maximum run:

| Model | Approx. processed tokens | Result | Elapsed |
|---|---:|---|---:|
| F16 | 2.8k, 8.3k, 21.9k, 43.8k, 80.1k, 120.1k | all anchors correct | 115 s at 120k |
| Q2_K | 2.8k, 8.3k, 21.9k, 43.8k, 80.1k, 113.8k | all anchors correct | 196 s at 114k |

The result is encouraging but deliberately narrow. It measures one synthetic long-context recall task, not degradation across the seven progressive subjects, multi-turn state, structured output, reasoning, uncertainty handling, or instruction hierarchy. It also measures prompt-processing latency: at the longest run, F16 processed roughly 1,061 prompt tokens/s and Q2_K roughly 583 prompt tokens/s in this setup.

## Behavioral ladder result

The fixed prompt contained seven subject checks: factual recall, staged arithmetic, structured output, coding, instruction hierarchy, uncertainty recovery, and long-context memory. The F16 model generated the answer sheet twice at each tier; Q2_K received the identical prompt once. Scores below are explicit subject-validator averages, with the F16 score shown as the control reference.

| Target / actual prompt tokens | F16 control | Q2_K | Q2_K deficit | Q2_K elapsed |
|---:|---:|---:|---:|---:|
| 4,096 / 4,214 | 0.786 | 0.786 | 0.000 | 3.4 s |
| 16,384 / 16,500 | 0.786 | 0.643 | 0.143 | 8.9 s |
| 32,768 / 32,885 | 0.786 | 0.595 | 0.190 | 18.8 s |
| 65,536 / 65,653 | 0.786 | 0.643 | 0.143 | 55.9 s |
| 98,000 / 98,117 | 0.786 | 0.571 | 0.214 | 82.1 s |

This is a real quality decline for Q2_K relative to the full-model answer sheet, although it is not perfectly monotonic. The strongest drop was near 100k. The Q2_K run also became much slower: at 98k, its cold prompt request took 82.1 seconds versus 49.5 seconds for the F16 control's first request at that tier.

The absolute validator score is not a truth score. The F16 control itself repeatedly answered the staged arithmetic as `18 + 7 * 3 = 51` (and once `54`) instead of applying the intended staged order to obtain 75. That is exactly why the answer sheet and an independent validator should both be retained: the former measures behavioral agreement, while the latter catches shared or reference-model mistakes.

The raw records are in `results/llama31-f16-vs-q2k/context-ladder-f16-vs-q2k.json`, generated by `scripts/context_ladder.py`. This ladder is still a one-turn stress prompt, not the full five-turn progressive session at every tier; that remains a more expensive follow-up if we need context-dependent multi-turn retention.

## Precision ladder result

Using the same prompt ladder, q8 KV cache, GPU placement, answer sheet, and 100k server limit:

| Weights | File size | 4k score | 98k score | 98k Q2/F16-style request time |
|---|---:|---:|---:|---:|
| F16 control | 16.07 GB | 0.786 | 0.786 | 49.5 s cold control request |
| Q8_0 | 8.54 GB | 0.786 | 0.786 | 76.2 s |
| Q6_K | 6.60 GB | 0.786 | 0.786 | 80.9 s |
| Q5_K_M | 5.73 GB | 0.714 | 0.786 | 82.5 s |
| Q4_K_M | 4.92 GB | 0.714 | 0.786 | 72.9 s |
| Q2_K | 3.18 GB | 0.786 | 0.571 | 82.1 s |

The simple seven-subject validator therefore shows a clear Q2 failure mode, but no meaningful quality separation among Q4_K_M through Q8_0 in this particular prompt. Q4 and Q5 had one low-context miss that disappeared at 16k; that is not a monotonic context effect. More discriminating tasks, more repeats, and the full multi-turn sessions are needed to rank the higher quants reliably.

Native FP8 was intentionally not included: the readily available Llama 3.1 FP8 weights are Safetensors intended for a different serving stack, while the directly runnable llama.cpp artifacts here are GGUF. Mixing runtimes would make the precision comparison less clean than this same-family GGUF ladder.

## Qwen3-8B-128K comparison

Qwen3-8B-128K was tested separately with its own BF16 answer sheet, YaRN enabled (`--rope-scaling yarn --rope-scale 4 --yarn-orig-ctx 32768`), and `/no_think` appended to every prompt. The same 100k server cap and five context tiers were used.

| Model | 4k | 16k | 32k | 64k | 98k |
|---|---:|---:|---:|---:|---:|
| BF16 control | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 |
| Q8_0 | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 |
| Q6_K | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 |
| Q5_K_M | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 |
| Q4_K_M | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 |
| Q2_K | 0.929 | 0.929 | 0.929 | 0.929 | 0.929 |

Unlike Llama 3.1, Qwen3 Q2_K did not worsen as context grew in this probe. Its constant 0.929 reflects one factual-answer formatting miss at every tier; it did not lose additional facts as the filler grew. Qwen3 Q8 required the asymmetric two-GPU split even at 100k; the other variants used the same split for consistency.

## Third-party altered Qwen3-8B comparison

The valid comparison uses [`DreamFast/qwen3-8b-heretic`](https://huggingface.co/DreamFast/qwen3-8b-heretic), a third-party altered Qwen3-8B with directly runnable F16, Q8_0, Q6_K, Q5_K_M, and Q4_K_M GGUFs. Every candidate was evaluated against the existing official Qwen3-8B BF16 answer sheet—not against an altered-model answer sheet. Thus `1.000` in the baseline column means the original Qwen3 control, and candidate scores are directly comparable to the official Qwen3 table above.

The same validator, `/no_think`, YaRN settings, 8-bit K/V cache, five context levels, and 100k cap were used. The altered GGUFs declare a 32k native context, so the runtime metadata was overridden to admit the 65k and 98k extrapolation runs; the actual server slot was 100,096 tokens.

| Model | 4k | 16k | 32k | 64k | 98k |
|---|---:|---:|---:|---:|---:|
| Official Qwen3 BF16 answer sheet | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 |
| DreamFast Heretic F16 | 0.381 | 0.333 | 0.310 | 0.190 | 0.262 |
| DreamFast Heretic Q8_0 | 0.262 | 0.333 | 0.310 | 0.143 | 0.429 |
| DreamFast Heretic Q6_K | 0.310 | 0.262 | 0.381 | 0.190 | 0.310 |
| DreamFast Heretic Q5_K_M | 0.143 | 0.262 | 0.190 | 0.381 | 0.310 |
| DreamFast Heretic Q4_K_M | 0.000 | 0.000 | 0.000 | 0.190 | 0.143 |

The main result is not a clean quantization cliff. The altered F16 control is already far below the official Qwen3 control on this structured multi-subject sheet. Q8/Q6/Q5 fluctuate around that weak result, while Q4 fails completely through 32k and only partially recovers at higher tiers. This indicates a large third-party-model quality/behavior gap before compression; the quant trend is secondary here.

The raw records are in `results/dreamfast-qwen3-8b-heretic/` as `context-ladder-f16.json`, `context-ladder-q8_0.json`, `context-ladder-q6_k.json`, `context-ladder-q5_k_m.json`, and `context-ladder-q4_k_m.json`. The earlier Rootkit7 4B run remains under `results/rootkit-bonsai-4b/` as an exploratory, non-comparable result.

## Huihui v2 altered Qwen3-8B comparison

As a second altered lineage, [`mradermacher/Huihui-Qwen3-8B-abliterated-v2-GGUF`](https://huggingface.co/mradermacher/Huihui-Qwen3-8B-abliterated-v2-GGUF) was tested using its directly provided F16 and Q6_K files. Both candidates used the same official Qwen3-8B BF16 answer sheet and the same context/runtime settings as the DreamFast run.

| Model | 4k | 16k | 32k | 64k | 98k |
|---|---:|---:|---:|---:|---:|
| Official Qwen3 BF16 answer sheet | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 |
| Huihui v2 F16 | 0.119 | 0.214 | 0.262 | 0.190 | 0.119 |
| Huihui v2 Q6_K | 0.119 | 0.071 | 0.262 | 0.190 | 0.167 |

Huihui v2 is as far below the original Qwen3 control as DreamFast, and its F16/Q6 scores are nearly indistinguishable. That strengthens the conclusion that the large quality loss is associated with these altered-model transformations, not ordinary weight quantization. The raw records are in `results/huihui-qwen3-8b-abliterated-v2/`.

## Fresh answer-oriented suite: official Qwen3 vs DreamFast Heretic F16

To separate answer quality from the earlier packed-JSON test, a fresh suite of 16 independent prompts was run. It includes arithmetic, logic, exact extraction, semantic answer equivalence, JSON schema validation, code, evidence handling, instruction hierarchy, and two long-context extraction tasks. The official model was run first and its actual answers were saved; the Heretic was then run on the identical prompts.

| Metric | Official Qwen3 BF16 | DreamFast Heretic F16 |
|---|---:|---:|
| Actual task correctness | 16/16 | 2/16 |
| Agreement with official answer class | — | 2/16 |

The two Heretic passes were the ordering question and the average-expression question; even those outputs were verbose or malformed. Several failures were substantive rather than formatting-only: arithmetic prompts were internally changed, exact identifiers were corrupted, the semantic bird question received “Yes,” JSON syntax was broken, and long-context markers were missed.

The full side-by-side answers are in [`official-vs-heretic-f16.json`](results/semantic-compare/official-vs-heretic-f16.json). The test implementation is [`semantic_compare.py`](scripts/semantic_compare.py), with sequential execution in [`run_task_suite.py`](scripts/run_task_suite.py).
